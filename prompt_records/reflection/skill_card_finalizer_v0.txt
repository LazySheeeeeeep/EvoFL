You turn one source-independent semantic center into one compact reusable Skill card.

The input contains a semantic_center, exactly two portable roles, and their
short contract. Build the card from those fields alone. Treat semantic_center
as the card identity and use the roles and contract to state its reusable
evidence test. Preserve their responsibility relationship and contract, while
choosing the shortest useful title, trigger, and knowledge.

Project Skill
Project Skill records stable system knowledge. Its center is a responsibility pattern and boundary contract, not a feature, library, pipeline implementation, or local API.

Choose a title and value that name the architectural responsibility: for example,
declarative-state reduction, representation-adapter contract, canonical-record
resolution, or configuration-to-execution handoff. Write a trigger with the
minimum observable roles and flow needed to recognize that responsibility in
another repository. A source may expose many implementation stages; retain only
the roles and handoff essential to the shared contract.

Write exactly three knowledge statements:
1. subsystem purpose and responsibility split: state why these roles form one
   organization, rather than merely that one invokes another;
2. state or control evolution: identify the representation, lifecycle state,
   configuration, or operation that changes at the central boundary;
3. diagnostic boundary: name the upstream responsibility boundary that should
   be inspected before downstream consumers when observed behavior diverges.

The third statement is a structural investigation aid, not a final ranking
rule. Do not emit a Project card whose three statements could describe any
generic producer-to-consumer handoff. When the semantic center only expresses
a generic transfer and lacks a distinct subsystem purpose or evolving state,
return the smallest faithful card but do not invent a broad canonical-record
or adapter-to-executor contract.

Each statement is one short sentence. Keep the full knowledge list below 960
characters. Prefer responsibility and representation words over mechanism
inventories. The trigger states one contract in at most 320 characters.
If a draft lists several transformations, preserve their shared handoff rather
than naming each transformation. If it lists several implementation roles,
retain the smallest role pair that still defines the boundary.

One-shot compression example. A draft may describe a source wrapper that buffers
fragments, converts representations, and calls a rendering API. Its card can be:
{
  "skill": {
    "value": "public_representation_to_delegate_contract",
    "title": "Public representation and delegated operation contract",
    "trigger": "Use when a wrapper presents a public representation while a delegated component accepts a different internal representation or operation contract.",
    "knowledge": [
      "The wrapper subsystem isolates public-input translation from execution so callers do not need to know the delegate's internal representation.",
      "Its central boundary transforms the public value into the delegate representation while preserving the metadata required for the operation.",
      "When output diverges, inspect the translation boundary before the delegate or final presentation layer because that is where public semantics can first be lost."
    ]
  }
}
The card intentionally omits buffering, byte conversion, terminal controls, and
the local wrapper name because they are incidental mechanisms rather than the
shared contract.

A source may also describe tokenization, context markers, hierarchy building,
and local predicate checks. Its portable Project center is a hierarchical
representation construction boundary: an upstream representation is composed
into a structured representation that a downstream interpreter relies on. The
trigger names those three responsibility roles. The knowledge states the
construction handoff and the interpreter's representation contract; local token
kinds, adjacency rules, and predicate names are evidence for that boundary,
not separate conditions for reusing the card.

Strategy Skill
Strategy Skill records one conditional localization decision family. Its center is a causal direction, the evidence test that separates alternatives, and the resulting rank order. Local component pairs are instances of this family rather than the identity of the card.

Build the identity around the diagnostic question and its discriminating
observation, not the particular kind of state observed in the source case.
For example, an error tuple, boolean mask, callable value, configuration
parameter, or type record can all instantiate one "first contract violation
across a responsibility handoff" decision when each is resolved by comparing
the state immediately before and after that handoff. In such a card, use
portable property categories such as representation, presence, ordering,
identity, type, or lifecycle state. Do not use a local state type as the
Strategy card's semantic center when the same before/after observation and
rank consequence would work for another property category.

A distinct Strategy card is warranted only when its source inspection differs
materially: for example, comparing parallel paths, comparing initialization
and execution lifecycle branches, or tracing ownership across a multi-step
transformation. A different field, value type, data container, or API name is
additional evidence for an existing decision family, not a new family.

Use the narrowest role names that are necessary to identify the inspection.
When the evidence test is simply whether a contract is already violated before
or only after one handoff, write the roles as an upstream responsibility and a
later responsibility boundary. Do not narrow that card to producer versus
resolver, normalizer, dispatcher, adapter, or executor unless the source
inspection genuinely requires a role-specific artifact that is absent from the
generic before/after comparison.

Name roles by their causal function: upstream representation constructor, downstream interpreter, public contract boundary, delegated implementation, state composer, state applier, producer, consumer, initializer, or reporter. Express a trigger as the causal direction and observable test between competing responsibilities. Prefer a family such as "origin versus later-boundary contract decision" when several local role pairs are resolved by the same before-and-after handoff observation.

When the semantic_center asks whether an incorrect state appears before or
after a handoff, write the generic origin-versus-later-boundary decision even
if the source draft involved encodings, buffers, indexes, output media, local
data structures, tuple shapes, missing-value sentinels, callable objects, or
configuration fields. Such terms are evidence and never define the title,
trigger, or knowledge. Preserve a distinct Strategy card only when its
semantic_center specifies a different causal direction or a different
observable test that changes the resulting rank.

Write exactly three knowledge statements:
1. compare the two responsibility paths;
2. state evidence favoring each alternative;
3. rank the first boundary whose contract contradicts the expected behavior.

Each statement is one short sentence. Keep the full knowledge list below 960
characters. The trigger states one competing responsibility pair and contract
question in at most 320 characters. Represent several local operations through
the one causal question they jointly answer.

One-shot compression example. A draft may compare a local transformer with an
output adapter while listing encoding, buffering, and formatting operations. Its
portable decision is upstream representation construction versus downstream
interpretation: inspect whether the representation is already invalid before
the handoff; an invalid value before the handoff favors construction, while a
valid value changed after the handoff favors interpretation.

Use normal prose in title, trigger, and knowledge. The value field is the only snake_case identifier.

Return exactly one JSON object:
{
  "skill": {
    "value": "stable snake_case semantic identity",
    "title": "portable human-readable title",
    "trigger": "one-sentence reusable applicability signature",
    "knowledge": ["exactly 3 concise portable statements"]
  }
}

Return JSON only.
