You prepare Project Skill retrieval and Strategy Skill selection for evolving a fault-localization SkillBank from one completed case.

The input contains:
- trajectory_evidence: repository, issue, compact staged trajectory, runtime Skill requests and load results, final Top-5, outcome, ground truth, and patch context;
- strategy_skill_catalog: every active Strategy Skill represented only by skill_id, title, and applicability trigger.

project_skill_query identifies the reusable subsystem architecture family demonstrated by the repository evidence. Express the family through its stable purpose, generic component roles, information flow, and responsibility boundaries. Prefer a family that can include adjacent boundaries in the same organization rather than naming one method, data field, local handoff, or defect. Replace repository and symbol identities with their architectural roles so the query remains applicable across different defects and repositories with the same organization.

Use an architecture-archetype query: it must remain meaningful after local domain objects are replaced. For example, express a reducer that turns declarative changes into canonical state as "declarative state transformation and reduction subsystem", rather than naming its particular operation, state field, or framework. The query is a retrieval description of the organization, not a summary of the observed feature.

strategy_diagnostic_context describes the diagnostic situation presented by this case: the generic competing candidate roles, their causal direction, the evidence already observed, and the unresolved question that prevents a reliable ranking. Express a reusable decision family rather than a local component pair. For example, an upstream constructor versus a downstream interpreter and a normalizer versus a consumer can both be described as whether an invalid state first appears before or after a responsibility handoff when the same handoff observation resolves the ranking.

First use patch_context to identify the changed responsibility boundary: the role whose contract, state transformation, or control decision was actually changed. Then use the trajectory to contrast that boundary with the Explorer's leading candidates. When the final Top-5 missed the changed boundary, express the diagnostic context that would have made its causal relationship to the observed symptom inspectable and rankable. This lets a failed exploration contribute a corrective decision pattern instead of merely repeating its initial hypothesis.

For every completed Top-5 miss with both a changed patch boundary and at least
one ranked candidate, make that contrast explicit. Name the changed boundary's
generic role first, name the leading wrong candidate's generic role second,
then state the unresolved causal question and the source observation that
separates them. Lifecycle differences are valid role contrasts: for example,
when the trajectory ranks an initializer but the patch changes the method that
executes or applies a state transition, describe an initializer-versus-
execution-boundary decision rather than a vague "transformation logic" issue.
This context is sufficient to create a new Strategy Skill when no catalog
trigger covers the same pair and question.

For example, when a patch changes an interceptor's capture, buffering, or representation-preservation behavior while the trajectory focused on environment detection, describe the unresolved decision as whether the symptom originates at the interception-and-handoff contract or at a downstream selection role. The concrete API names are evidence; the query should retain only the competing responsibilities and the observation needed to distinguish them.

Select selected_strategy_skill_id when one catalog trigger covers the same causal direction, evidence test, and ranking consequence. Local component names and domain-specific contracts may differ when the card still resolves the same decision family. Use null when no trigger covers the required diagnostic structure. The catalog does not contain Skill knowledge; selection is based only on applicability, and the selected knowledge will be tested against repository evidence later.

Each text field should express one semantic target in one information-dense sentence. Target 200-350 characters and keep the field under 800 characters. Retain only the roles, flow, boundary, and unresolved decision needed for retrieval; omit implementation details and repeated evidence.
Write both semantic targets so they remain meaningful after replacing the repository, class, function, and constant names with generic architectural or candidate roles.

Return exactly one JSON object:

  "project_skill_query": "compact system-structure retrieval query",
  "strategy_diagnostic_context": "compact description of candidate relationships, observed evidence, and unresolved decision",
  "selected_strategy_skill_id": "catalog skill_id or null",
  "strategy_selection_reason": "compact trigger-matching explanation"
}

Return JSON only.
